> **Статус: ACTIVE — TEST-01 FULL PASS (12.10.2026).** Модуль `BT18-T` через CH340 `COM4` при 9600 бод ответил **на все 8/8 AT-команд**, включая версию `V3.01`, имя `BT18-T`, настройку скорости `BAUD=1`, PIN и UUID. ## 0. Быстрый запуск лаборатории (PowerShell)

Нужны Python 3.10+ и Bluetooth-адаптер компьютера для BLE-теста. Проверить Python:

```powershell
py --version
```

Если Python отсутствует, установите его с https://www.python.org/downloads/windows/ и откройте новый PowerShell. Из корня клонированного репозитория:

```powershell
py --version
py -m pip install --user -r .\DX-BT18\tools\requirements.txt
py .\DX-BT18\tools\bt18_probe.py --list-ports
```

Подключите модуль через адаптер USB-UART с логическими уровнями **3,3 В**. Подставьте фактический COM-порт (пример `COM4`):

```powershell
py .\DX-BT18\tools\bt18_probe.py --port COM4 --baud 9600 --profile dual
```

Если у вас BLE-only вариант или dual-mode не отвечает, разрешён второй профиль *чтения*:

```powershell
py .\DX-BT18\tools\bt18_probe.py --port COM4 --baud 9600 --profile le
```

BLE-поиск с ПК:

```powershell
py .\DX-BT18\tools\bt18_ble_scan.py --duration 10 --name BT18
```

Не используйте `--name BT18`, если устройство может рекламироваться под неизвестным именем: выполните полный поиск без фильтра.

После сканирования для **конкретного** найденного BLE-идентификатора можно получить карту GATT:

```powershell
py .\DX-BT18\tools\bt18_ble_scan.py --address "DEVICE_ID_FROM_SCAN"
```

Этот шаг устанавливает BLE-соединение для перечисления сервисов. Он не записывает характеристики и не прошивает модуль. BLE-сканирование **не** проверяет Classic Bluetooth/SPP.

Подробные параметры скриптов: [инструменты DX-BT18](tools/README.md).

## Тест кнопки для AT-режима — актуальная инструкция

В оригинальном руководстве DX-SMART DX-BT18 контакт радиомодуля **P26 = GPIO25** переводит двухрежимный модуль в AT-режим при удержании **LOW**. Типовая схема из руководства показывает кнопку `KEY1` от этого входа к GND. Поэтому **если кнопка на нашей переходной плате действительно выполняет эту функцию**, нажимать её следует **во время передачи команды**, а не просто кратковременно до теста.

**Важно:** для немаркированного устройства `BT18-T` назначение кнопки ещё не подтверждено. Не применяйте к нему по умолчанию инструкции HC-05 «удерживать при подаче питания», не держите кнопку долго, чтобы случайно не вызвать сброс настроек. Нет подтверждения, что кнопку вообще подключили к P26.

Для удобства в утилиту добавлены `--command` (одна безопасная команда) и `--start-delay` (обратный отсчёт).

Из корня репозитория после `git pull --ff-only`:

```powershell
py .\DX-BT18\tools\bt18_probe.py --port COM4 --baud 9600 --profile dual --command "AT+TEST" --start-delay 3 --timeout 0.6
```

**Порядок:** модуль уже запитан, Bluetooth-соединение с телефоном отключено; запустить команду; когда программа покажет `Sending in 1...`, нажать кнопку на плате и удерживать до появления строки результата `AT+TEST`; затем **сразу отпустить**. Таким образом кнопка удерживается около 1–2 секунд, а не на протяжении всех восьми AT-команд. Одно короткое нажатие без удержания во время самой передачи для оригинального DX-BT18 недостаточно.

При наличии корректного AT-режима оригинальная прошивка должна ответить `OK`. Если результата нет, можно один раз повторить с `--command "AT+NAME?"`, но отсутствие ответа **не доказывает** аппаратной неисправности или неправильности схемы: реальный модуль может иметь другую прошивку или назначение кнопки. Не переходить к изменению проводов, перепрошивке или длинному удержанию без идентификации.

**Источники:** [DX-SMART DX-BT18, разделы 9 и 12](https://manuals.plus/m/b2042a61df3340ba1f528646b16efdf3d786b18f2edb66204799996c10bea264); [схема KEY1 из статьи со схемой включения DX-BT18](https://blog.csdn.net/weichen_78/article/details/128682285). См. также [отдельную инструкцию по кнопке и ограничениям](docs/BUTTON_AT_MODE.md).

## 1. Объект исследования и ограничения

- Покупка: модуль под названием DX-BT18 без маркировки на металлическом RF-экране.
- Аппаратный производитель и SoC **не установлены**.
- Оригинальная DX-SMART документация — справочник для сравнения, **не сертификат** нашей платы.
- Номинально DX-BT18 — Bluetooth 4.2 Classic SPP + BLE UART; существует другая ветвь BT18-LE (BLE-only).
- **Статус DX-BT18: TEST-01 UART AT FULL PASS (12.10.2026).** По консольному выводу пользователя, модуль `BT18-T` корректно ответил на **8/8 запросов** через `COM4`, 9600 бод. Прочитаны конфигурация и `V3.01`. Пользовательский Bluetooth-адрес получен, но **не публикуется полностью** в открытом репозитории. Функции Classic SPP, BLE GATT и происхождение чипа не аттестованы. [Результат](tests/TEST-01_AT_UART_RESULT_2026-10-12.md) · [предыдущие наблюдения](tests/OBSERVATIONS_2026-10-11.md).

Две независимые группы свидетельств: (а) ответы AT по UART и (б) фактическая BLE-реклама/GATT. Совпадающие имена, UUID или версия AT **не подтверждают** оригинальность чипа.

## 2. Соединение без риска для клона

```text
USB-UART 3.3 V logic       BT18 MODULE (signals must be confirmed)
TX ---------------------> RX
RX <--------------------- TX
GND -------------------- GND
3.3 V regulated -------- VCC (bare module only)
```

- Не подавать 5 В на UART RX или VCC **голого радиомодуля**. Некоторые платы-переходники имеют собственный стабилизатор, но это надо подтверждать по плате.
- Не подключать к неизвестным контактам `ICE`, `VPP`, `KEY` или `P26` по одной лишь похожей надписи/внешности.
- **Ограничение данного стенда: только четыре провода** — TX, RX, VCC и GND. Дополнительные выводы не подключаем, не запрашиваем и не считаем обязательным условием первого этапа.
- По руководству **оригинального dual-mode DX-BT18** контакт **P26 (GPIO25)** требуется удерживать LOW для AT-режима; **BT18-LE** может вести себя иначе. На нашем четырёхпроводном стенде этот вход недоступен: если AT не отвечает, фиксируем **AT ACCESS NOT ESTABLISHED**, а не неисправность. Перепайку и дополнительные контакты не предлагаем.
- Если AT недоступен, проверяем доступный прозрачный UART-обмен (при установленном Bluetooth-соединении) и отдельно BLE advertising/GATT. BLE-тест выполняется по радиоканалу, дополнительных проводов не требует.
- В руководстве **оригинального DX-SMART** заводские UART **9600, 8N1**, без аппаратного flow control; в разделе испытаний скорости передачи встречается 115200. Реальная скорость нашего немаркированного `BT18-T` **не определена**. Команды оригинала завершаются `CRLF`; на других прошивках может отличаться.
- Освободите COM-порт (закройте Serial Monitor/другие клиенты). На время AT-проверки желательно отключить Bluetooth-подключения.
- Отсутствие ответа при неверном режиме AT **не равно неисправности** модуля.

[TEST-02A: подтверждённое BLE-вещание на Python 3.14](tests/TEST-02_BLE_DISCOVERY_2026-10-12.md): `BT18-T`, адрес `98:DA:F0:00:EE:27`, сервис `FFE0`. Для GATT нужен отдельный тест.

## 4. Доступные «регистры» и прошивка

Документированные AT-команды работают с логическими конфигурационными полями. Это **не регистры памяти SoC**. BLE GATT-характеристики — также не адреса физических регистров.

Оригинальное руководство обозначает **P8/ICE** как порт обновления firmware и **P7/VPP**. Оно не предоставляет проверенного открытого комплекта «firmware + programmer + процедура восстановления» для нашего неидентифицированного образца. Команды для чтения/записи произвольных адресов RAM, FLASH, OTP, периферии в AT-руководстве отсутствуют.

**Перепрошивка отложена**, пока не установлены SoC, назначение контактов, тип памяти, совместимый софт и способ восстановления. Не подавать экспериментальные напряжения на ICE/VPP.

Отдельные решения на YiChip YC1021 используют внешнюю EEPROM для конфигурации, но **карта EEPROM из сторонней платы не является картой DX-BT18**. Даже если будут совпадения в сигналах, не приравнивать без измерений кристалл DX1022 к YC1021.

## 5. GitHub-first порядок для читателей и автора

1. Исправления кодов и инструкций вносятся в этот GitHub-репозиторий.
2. Читатель выполняет `git pull --ff-only`, затем запускает нужный тест.
3. Консольные результаты/снимки измерений передаются отдельно и заносятся в `RESULT_YYYY-MM-DD.md` **только при наличии фактических данных**.
4. Различать `PASS`, `PARTIAL`, `FAIL`, `PENDING`; не выдавать гипотезы об идентичности за подтверждённое происхождение.
5. После 2–3 осмысленных проверок при отсутствии прогресса фиксировать ограничения и прекращать работу с конкретным экземпляром без бессрочного «ремонта».

Личные дампы могут содержать MAC-адреса окружающих устройств. Не публикуйте их без очистки. Локальные `results/` исключены из Git.
